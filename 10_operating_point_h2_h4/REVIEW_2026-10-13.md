# E10 code review (operating point, H2-H4): correctness and pre-registration conformance

Reviewed: `origin/exp/10_operating_point_h2_h4` at 18e7992 (copies under `e10review/head/`). The running main job uses code commit 78aa94a and the split job uses 2e1ce11. Between 78aa94a and 2e1ce11, `analyze()` and the 09 modules are unchanged; the only change is that `_prep`/`analyze_part`/`merge_parts` were added. Review was read-only. Local tests used `spikes_v2.npz` from the handoff zip (`test1.py`, `test2.py`, `probe*.py` in this folder).

## Verdict on the running jobs

- **No critical bug was found in the step-2 computation.** The jobs don't need to be killed. The pre-registered constants are correct: windows, basis, the bin-400 origin, the exclude filter, subset size and count, number of shuffles, and shuffle semantics. thermo() and the empirical covariance match brute-force checks. The split path gives bit-identical results to `analyze()`.
- **The running job is still affected in four ways that a post-hoc fix can't recover** (S2-1 to S2-4 below): (1) it uses its own folds, not the pre-registered `fold_k`; (2) it saves only summary statistics of the null, not the 20 per-shuffle values, so the pre-registered session-level null test can't be computed; (3) it doesn't record convergence for the null and fold fits; (4) the pre-registered sensitivity analyses (all reaches; subset check vs full population at N = 17-19) aren't run. Fitted (h, J) aren't saved either, so any of these needs refits.
- **step3_stats.py has one critical and several major errors** (S3-1 to S3-5). It hasn't run yet. **Fix it before reading results.** The worst one: H3b significance is counted as *support* for H3, when the pre-registration says it *refutes* fixed J.

## Issues

### S3-1 · step3_stats.py:46-55 · H3b's logic is inverted in the primary family · **critical** · confidence high
- What's wrong: `fam3["H3"] = max(p_H3a, p_H3b)` is BH-adjusted, and a small value is read as "H3 holds". Under the pre-registration, a significant H3b refutes fixed J. §5 H3(b) says it "must not improve held-out likelihood (Wilcoxon, p > 0.05) … If it does improve … the 'fixed J' part of the claim fails". Amendment 2 says "Test: κ̂ ≠ 0 across sessions (Wilcoxon)". §6 lists "epoch-specific J improves prediction (H3b)" under **Refuted**.
- Failure scenario: κ̂ > 0 consistently (J really does scale up in the reach window, p = 0.001), and H3a's Spearman has p = 0.01. Then H3 gets p_FDR ≈ 0.015, and the table shows H3 as passing FDR when it should be refuted.
- Fix: H3 holds only if H3a is significant with ρ > 0 and same-sign agreement, AND H3b is non-significant (p > 0.05, with effect size reported). Don't fold H3b's p into BH as evidence for H3.

### S3-2 · step3_stats.py:31-35, 46 · H3a uses the sensitivity prediction as primary · **major** · confidence high
- What's wrong: the primary H3a entry (`prim["H3a"]`) correlates `emp_dcov` with `pred_dchiJ_folds`. Pre-reg §5 H3(a) says the empirical change "is compared with the fixed-J prediction Δχ_J/N **from the full-data fit** … **Sensitivity:** the prediction averaged over the 5 fold fits". The code runs the full-data comparison (`real_dchiJ`, line 34) but leaves it out of the family. The per-session sign agreement (`n_pos`, line 33) also uses the fold prediction. No test is attached to that sign agreement, and the frozen-field reference (Δ = 0) isn't reported.
- Failure scenario: the fold-averaged prediction is noisier, since each fold fit is trained on about 13 of 17 reaches. It could make H3a fail or pass when the pre-registered full-data comparison does the opposite.

### S3-3 · step3_stats.py:29, whole file · H3b's held-out gain is never tested · **major** · confidence high
- What's wrong: step 2 computes `kappa_gain_reach`, but step 3 never uses it. The pre-reg (§5 H3b, amendment 2) requires "the held-out gain of the κ model" (Wilcoxon, effect size). Only κ̂ is tested.
- Failure scenario: κ̂ ≠ 0 is driven by poorly identified κ when J ≈ 0. Locally, condition 210622_0 (N = 3) gave κ̂ = +1.65 with a negligible gain. That would be reported as a J change with no held-out evidence.

### S3-4 · step3_stats.py:60 · Both pre-registered mixed models are missing · **major** · confidence high
- What's wrong: §5 H2 requires "a mixed model ΔI ~ 1 + (1 | mouse) over the 6 mice". §5 H4a requires "a mixed model ΔI ~ Δv + (1 | session)". Neither is fitted. The comment says mouse isn't available, but the mouse ID is in `reextract_reaches.csv` / `reextract_sessions.csv` (column `mouse`, parsed from `Dylan_<date>_<mouse>_NPresults`). The H4a model doesn't need mouse at all.

### S3-5 · step3_stats.py:17, 63 · The H2 null comparison isn't the pre-registered one · **major** · confidence high
- What's wrong: the pre-reg says "The real **session** ΔI must exceed the 95th percentile of **its own null**." The code compares per condition (`real_dI > null_dI_p95`), where for N > 20 the p95 is averaged over subsets. A session then counts if at least 50% of its conditions exceed. The 50% rule is invented, and the count is only printed, not tabulated or gated. The faithful test needs the session-mean null distribution: for each shuffle index b, average ΔI_null over the session's conditions (and over subsets), then take p95. The running job doesn't save per-shuffle values (see S2-2).
- Failure scenario: a session with 3 conditions, where 2 exceed and 1 is far below, "passes" even though its mean ΔI is under the session-null p95. The reverse can also happen.

### S3-6 · step3_stats.py:10-19 · Silent drops: missing tasks, non-converged fits, NaNs · **major** · confidence high
- What's wrong: no check that all 63 conditions are present, or all 10 subsets for N > 20. `n_tasks` is recorded but never asserted. Conditions with fewer subsets, or sessions missing conditions (for example if the N = 19 tasks time out), are averaged anyway. `converged` / `kappa_converged` are averaged like any other number, and non-converged fits are neither excluded nor flagged. `wilcoxon()` (line 24) drops NaNs, and only `n` reveals it. The Spearman tests use `nan_policy="omit"` while still reporting `n=len(cond)`.
- Failure scenario: step 3 runs while the 6 N = 19 conditions (220515, 220516) are unfinished. Those 2 sessions drop out of n = 21 silently, and nothing else shows it in the tables.

### S3-7 · step3_stats.py · Pre-registered sensitivity analyses are missing · **major** · confidence high
- The N ≥ 5 restriction (§1) isn't implemented. The all-1249-reaches sensitivity (§1) isn't implemented in step 2 or step 3, since there's no flag to skip the exclude filter. The amendment-1 check isn't implemented: "in the four sessions with N = 17-19, the subset estimate is compared with the full-population estimate". Step 2 never makes 16-subsets for N ≤ 20. The late window (+50..+150, exploratory) isn't computed, and it can't be from the saved outputs because thermo is evaluated only on rows 300:420.

### S3-8 · step3_stats.py:36-37, 51-52 · Minor statistical details · **minor** · confidence high
- BH q-values aren't clipped at 1. The decision rule needs ρ > 0 (H4a) and ΔI > 0 (H2), but the p-values are two-sided and the sign isn't checked in code. That's fine if a human reads the medians, but the script doesn't enforce it. The H4a and H3a Spearman tests use n = 63 conditions, which aren't independent within session. That is what the pre-registration specifies, but it conflicts with §5's "unit = session" and should be stated.

### S2-1 · e10_lib.py:92 (and :125, split path) · CV folds ignore `fold_k` · **major** · confidence high
- What's wrong: `fold = np.arange(R) % 5` interleaves the kept reaches. The data carry the original 5-fold assignment `fold_k` (`export_spikes_v2.py`: `rng(stim).permutation`, `array_split`), which earlier analyses use as `fold[keep]` (`run_static_ll.py:14`). Pre-reg §5 H3(b) says "(exact maximum likelihood, **the same folds**)". On every condition checked, `fold_k[keep]` ≠ `arange % 5`. (Step 1 synthetic also used `arange % 5`, which is harmless there.)
- Impact: no leakage and no expected bias, since both models are trained on the same training reaches. But the H3b held-out gain and the fold-averaged Δχ_J differ from the pre-registered values, and with about 17 reaches the fold choice matters for the gain's sign in individual conditions. **The running job is affected** (not recoverable without refitting the κ/CV part).

### S2-2 · e10_lib.py:88-89 · Per-shuffle null values aren't saved · **major** · confidence high
- What's wrong: only `null_dI_mean`, `null_dI_p95`, `null_dI_max`, `null_rho_mean` and `null_dchiJ_mean` are stored. The session-level "exceed own null p95" test (S3-5) needs the 20 per-shuffle ΔI values per task, aligned by shuffle index b, to build each session's null distribution. Averaging p95 across conditions/subsets is not the p95 of the averaged null. It is usually larger, so the test becomes conservative, but it isn't the pre-registered test. **The running main job is affected.** The split job's `part_*.pkl` files do keep per-shuffle values `(b, dI, rho, dchiJ)`, so don't delete them.

### S2-3 · e10_lib.py:86, 96 (thermo_model.fit_exact maxiter=500) · Null and fold fit convergence isn't recorded · **major** · confidence medium
- What's wrong: `converged` is stored only for the real fit and the full κ fit. The 20 shuffle refits and 5 fold refits run with `maxiter=500` and are never checked. Locally, N = 8 (210512_2) needed 425 iterations. RUN_LOG 20:02 says 2022 conditions need about 3x more iterations than N = 16, so 500 can be hit. A truncated L-BFGS fit violates the exact-ML / moment-matching premise (§2).
- Failure scenario: in the strongly coupled 2022 sessions, the shuffle refits stop at 500 iterations. Shuffled data have J ≈ 0 and usually converge faster, so the risk is mainly to the real and fold fits. Real fits are at least flagged; fold fits (which feed `pred_dchiJ_folds` and the gain) aren't. Recommendation: after the run, report the fraction of real/κ fits with `converged=False` per cohort. Fold and null convergence can't be audited from the outputs.

### S2-4 · e10_lib.py:13-15, 81-82 · Window endpoints are half-open · **minor** · confidence medium
- Pre-reg §4: "Baseline: bins −100 to −40"; "Reach: bins −20 to +20". The code uses `300:360` (−100..−41) and `380:420` (−20..+19). If the pre-reg is read as inclusive, bins −40 and +20 are dropped. This is applied consistently to the real fit, null, empirical covariance and κ (`EM[380:420]`; amendment 5 says "bins 380-420"), so it is only a minor deviation. State "half-open [380, 420)" in RESULTS.

### S2-5 · merge_step2.py:9-10 · The equality check is weak in a few cases · **minor** · confidence high
- `np.isclose(nan, nan)` is False, so any NaN field (for example `pred_dchiJ_folds`, or `rho` for N < 3) prints a spurious MISMATCH. A real mismatch is only printed and never stops the merge or chooses a version. Keys present only in the main file aren't compared. A task copied from the split dir while the main job is mid-computation gets overwritten silently when the main job finishes (`pickle.dump` without an existence check), with no comparison. Results are identical, so the impact is negligible.

### S2-6 · step2_real_h2_h4.py:29 · One exception kills the whole pool · **minor** · confidence high
- `list(pool.imap_unordered(...))` re-raises the first task exception in the parent. The `with Pool` block then terminates every in-flight task: hours of N = 19 work, discarded with no pickle written. The resume logic limits the damage. Also, the `pickle.dump(open(fn,'wb'))` write isn't atomic, so a kill during the write leaves a truncated pkl. A rerun then skips that task, and step 3 crashes on load.

### S2-7 · e10_lib.py:74, step2:26 · Subsets differ across the 3 conditions of a session · **minor** · confidence high
- The seed `1000*i + int(key without "_")` includes the block, so each condition of an N > 20 session uses different 16-neuron subsets. Amendment 1 only requires the same subsets for real and null, which holds. The session mean then mixes different neuron sets, which adds variance but no bias. Seed collisions across keys are possible (for example 210608_2 with i=1 and 210708_2 with i=0) but harmless.

### S2-8 · e10_lib.py:24-46 · κ is unpenalized and poorly identified when J ≈ 0 · **minor** · confidence medium
- κ only scales J. When J is near 0 (small N, weak coupling), κ̂ can be very large (+1.65 at N = 3, 210622_0). That passes the pre-registered synthetic check, but session means of κ̂ can be dominated by such conditions. Wilcoxon is rank-based, so only the sign matters, but report κ̂ alongside the gain (see S3-3).
